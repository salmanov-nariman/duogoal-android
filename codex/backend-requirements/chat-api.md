# Инструкция для backend-команды: чаты DuoGoal

## Что должен уметь Android-клиент

Открыть диалог с партнёром, показать список чатов и сохранённую историю, отправить текст, получить новые сообщения без обновления экрана, показать непрочитанные и отметку «прочитано». После перезапуска приложения и обрыва сети история не теряется, повторная отправка не создаёт дубликаты.

Ниже — **предложение контракта для согласования**, не описание уже реализованного API. Если у backend есть эквивалентные маршруты или схемы, достаточно согласовать их и предоставить примеры. Требуются гарантии поведения, а не конкретная внутренняя архитектура сервиса.

Первая версия: личные текстовые диалоги двух пользователей. Группы, вложения, редактирование/удаление сообщений, поиск по истории и звонки в этот контракт не входят. Push-уведомления выделены отдельно в конце.

## 1. Общие правила — CHAT-001

- REST: `https://hlt.com/api/chat`; WebSocket: `wss://hlt.com/api/chat/ws`.
- Все REST-запросы и WebSocket handshake: `Authorization: Bearer <accessToken>`. JSON-тело: `Content-Type: application/json`.
- Пользователь определяется только по проверенному JWT. Если gateway передаёт `X-User-Id`, он удаляет подставленный клиентом заголовок; прямой публичный доступ к внутреннему сервису исключён.
- Не принимать `senderId` или «текущий userId» из тела как источник прав. Проверять участие в чате на каждом запросе и при доставке событий.
- JSON — `camelCase`; идентификаторы — строки UUID; время — серверное, ISO 8601 UTC. Nullable-поля присутствуют со значением `null`.
- `sequence` — положительный целочисленный номер сообщения внутри одного чата, назначенный сервером. Возрастает в порядке фиксации сообщений, не повторяется; пропуски допустимы. Ограничение: безопасный JSON integer, до `9007199254740991`. Время не использовать как единственный ключ сортировки.
- `revision` — возрастающая версия состояния чата: меняется при новом сообщении, прочтении и изменении метаданных. В REST и событиях помогает не заменить свежие данные устаревшими.
- Предлагаемые ограничения: текст до 4000 Unicode code points, `limit` для списка 1–50 (по умолчанию 20), для сообщений 1–100 (по умолчанию 50). Невалидный limit — `400`, не молчаливое изменение. Ограничить также размер HTTP/WS payload.
- Текст из одних пробельных символов запрещён; у допустимого текста сохраняются пробелы и переносы. Не возвращать HTML вместо JSON при ошибке gateway.

## 2. Общие модели

### Message

Все успешные отправки, страницы истории и события содержат одинаковый полный объект:

```json
{
  "id": "44444444-4444-4444-8444-444444444444",
  "chatId": "11111111-1111-4111-8111-111111111111",
  "senderId": "22222222-2222-4222-8222-222222222222",
  "clientMessageId": "55555555-5555-4555-8555-555555555555",
  "sequence": 42,
  "text": "Привет! Начнём сегодня?",
  "createdAt": "2026-10-26T12:00:00Z"
}
```

`clientMessageId` создаёт Android до отправки и сохраняет для повторных попыток. `id`, `sequence`, `createdAt` назначает сервер. Состояние «отправляется/ошибка» — локальное; успешный ответ означает «сохранено сервером», не «доставлено на устройство партнёра».

### Chat — представление для текущего пользователя

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "title": "Миша",
  "partner": {
    "id": "33333333-3333-4333-8333-333333333333",
    "username": "misha",
    "displayName": "Миша",
    "avatarUrl": null
  },
  "lastMessage": {
    "id": "44444444-4444-4444-8444-444444444444",
    "chatId": "11111111-1111-4111-8111-111111111111",
    "senderId": "22222222-2222-4222-8222-222222222222",
    "clientMessageId": "55555555-5555-4555-8555-555555555555",
    "sequence": 42,
    "text": "Привет! Начнём сегодня?",
    "createdAt": "2026-10-26T12:00:00Z"
  },
  "lastSequence": 42,
  "myLastReadSequence": 40,
  "partnerLastReadSequence": 41,
  "unreadCount": 1,
  "revision": 57,
  "createdAt": "2026-10-25T10:00:00Z",
  "updatedAt": "2026-10-26T12:00:00Z"
}
```

- `title` — готовый заголовок диалога; `displayName` может быть `null` (fallback — username). `avatarUrl` — публичный HTTPS URL либо `null`. Email и другие приватные данные партнёра не нужны.
- У пустого чата `lastMessage: null`, `lastSequence: 0`, обе отметки прочтения и `unreadCount` — `0`.
- `unreadCount` считает только сообщения партнёра после моей отметки прочтения, а не разницу sequence. Собственные сообщения его не увеличивают.
- Собственное сообщение прочитано партнёром, если его `sequence <= partnerLastReadSequence`.
- `updatedAt` — время создания чата/последнего сообщения; прочтение не поднимает чат в списке. `revision` при прочтении при этом увеличивается.

## 3. Создать или получить диалог — CHAT-006

`POST /api/chat/chats`

```json
{
  "partnerId": "33333333-3333-4333-8333-333333333333"
}
```

Ответ: `201 Created` и объект `Chat` при создании, `200 OK` и тот же чат, если диалог уже есть. Текущий пользователь добавляется автоматически. Запрос не принимает произвольный список участников.

Предложение: один диалог на неупорядоченную пару пользователей. Одновременные запросы с двух устройств/от двух участников не создают два чата — уникальность гарантируется сервером, не только предварительным SELECT. Нельзя создать чат с собой (`400 INVALID_PARTNER`); неизвестный партнёр — `404 USER_NOT_FOUND`.

**До реализации нужно согласовать продуктовое правило:** разрешён ли чат с любым пользователем или только после принятия приглашения к цели? Во втором случае сервер проверяет связь/приглашение и возвращает `403 CHAT_NOT_ALLOWED` при отсутствии допуска. Если нужен отдельный чат для каждой цели, вместо уникальности пары потребуется `goalId` в запросе и модели и уникальность по цели. Не реализовывать оба варианта наугад: backend-команда подтверждает выбранный вариант.

Если чаты создаются автоматически при принятии приглашения, отдельный POST может не понадобиться: тогда API принятия приглашения должен вернуть `chatId`, а повторное принятие — тот же идентификатор.

## 4. Список чатов и один чат — CHAT-002

`GET /api/chat/chats?limit=20&cursor=<opaque-cursor>`

- На первой странице `cursor` отсутствует. Ответ `200`: `{ "items": [Chat], "nextCursor": "..." }`; `Chat` здесь обозначает полный объект из раздела 2.
- Последняя страница: `nextCursor: null`. Нет чатов: `items: []`, `nextCursor: null`.
- Сортировка: `updatedAt DESC, id DESC`. Cursor непрозрачен для клиента, связан с текущим пользователем и параметрами запроса.
- Страницы должны перечислять стабильный набор и порядок чатов на момент первого запроса (snapshot cursor), чтобы одновременное сообщение не вытеснило ещё не загруженный чат между страницами. Поля объектов могут отражать более новую revision.
- Просроченный snapshot — `410 CURSOR_EXPIRED`: клиент загружает список заново. Объявить TTL cursor, предложение — 10 минут. Невалидный/чужой cursor — `400 INVALID_CURSOR` без раскрытия данных.

`GET /api/chat/chats/{chatId}`

Ответ `200`: полный `Chat`. Нужен для открытия диалога по идентификатору, актуальных данных партнёра, счётчиков и восстановления после reconnect.

## 5. История сообщений — CHAT-003

`GET /api/chat/chats/{chatId}/messages?limit=50&cursor=<opaque-cursor>`

```json
{
  "items": [],
  "nextCursor": null
}
```

В `items` — полные объекты `Message`. Первая страница без cursor содержит последние сообщения, порядок `sequence DESC`. Следующий cursor продолжает строго старее последнего элемента страницы; новые сообщения не сдвигают страницы и не создают дубли. Пустая история — `200` с пустым массивом, не `404`. `nextCursor: null` означает, что более старых сообщений нет.

Cursor связан с чатом, пользователем и направлением запроса. Если его срок действия истёк — `410 CURSOR_EXPIRED`; история загружается заново. Для загруженной истории клиент отображает сообщения в обратном, хронологическом порядке.

## 6. Отправить и сохранить сообщение — CHAT-004

`POST /api/chat/chats/{chatId}/messages`

```json
{
  "clientMessageId": "55555555-5555-4555-8555-555555555555",
  "text": "Привет! Начнём сегодня?"
}
```

- Новый запрос: `201 Created`, полный `Message`.
- Повтор с тем же `(senderId, chatId, clientMessageId)` и тем же текстом: `200 OK`, **тот же** Message с исходными `id`, `sequence`, `createdAt`. Проверка выполняется атомарно и при параллельных запросах. Запись для dedup живёт не меньше самого сообщения.
- Тот же ключ с другим текстом: `409 CLIENT_MESSAGE_ID_CONFLICT`, не изменение существующего сообщения.
- Проверить права, сохранить сообщение, обновить состояние чата, затем публиковать событие. После успешного ответа сообщение обязано быть доступно в истории и после рестарта сервиса.
- Не подтверждать успех до сохранения. Устранить окно «транзакция сохранена, процесс упал до публикации» надёжной доставкой событий (например, transactional outbox). Конкретное решение выбирает backend-команда.
- Событие может прийти отправителю раньше HTTP-ответа; оба содержат одинаковые идентификаторы для объединения. Повторы событий допустимы, создание второго сообщения — нет.

У потерянного HTTP-ответа результат неизвестен: Android повторит запрос с прежним `clientMessageId`, не с новым. Отправка выполняется через REST; второй протокол отправки через WebSocket в первой версии не нужен.

## 7. Отметить прочитанным — CHAT-007

`PUT /api/chat/chats/{chatId}/read`

```json
{
  "lastReadSequence": 42
}
```

Ответ `200`: актуальный полный `Chat` для вызывающего пользователя, включая `myLastReadSequence`, `unreadCount`, `revision`.

- Sequence должен соответствовать существующему сообщению этого чата (либо `0` для начальной отметки); значение из будущего/неизвестное — `400 INVALID_READ_POSITION`.
- Сервер хранит `max(старое значение, новое значение)`. Повтор или запоздавший запрос не откатывает прочтение назад.
- Нельзя просто обнулить счётчик: новое сообщение, пришедшее после указанной позиции, остаётся непрочитанным.
- Отметка общая для аккаунта, не для конкретного устройства. Все устройства обоих участников получают `chat.read` и обновлённый `Chat`.
- Прочтение сообщает клиент, когда сообщения реально показаны в открытом диалоге, не при одном лишь получении WebSocket-события.

## 8. Реальное время — CHAT-005

Handshake: `GET wss://hlt.com/api/chat/ws`, `Authorization: Bearer <accessToken>`, успешный upgrade — `101`. Токен не помещать в URL. Gateway должен поддерживать upgrade и достаточно длинный idle timeout.

Одно соединение получает события всех чатов текущего пользователя, без отдельной подписки на каждый chatId. Отправитель также получает собственные сообщения — на всех своих устройствах. Сервер не рассылает события посторонним пользователям.

После регистрации соединения в рассылке сервер присылает:

```json
{
  "type": "connection.ready",
  "payload": { "heartbeatIntervalSeconds": 25, "heartbeatTimeoutSeconds": 10 }
}
```

Только после `connection.ready` клиент начинает REST-синхронизацию; пришедшие во время неё события буферизует и объединяет по идентификаторам/версиям.

### События

| type | payload | Когда |
|---|---|---|
| `message.created` | полный `Message` | новое сохранённое сообщение |
| `chat.updated` | полный `Chat` именно для получателя | создан чат, пришло сообщение, изменилось прочтение/метаданные |
| `chat.read` | `chatId`, `userId`, `lastReadSequence`, `readAt`, `revision` | участник продвинул прочтение |

Формат envelope для всех трёх событий:

```json
{
  "eventId": "66666666-6666-4666-8666-666666666666",
  "type": "chat.read",
  "occurredAt": "2026-10-26T12:01:00Z",
  "payload": {
    "chatId": "11111111-1111-4111-8111-111111111111",
    "userId": "33333333-3333-4333-8333-333333333333",
    "lastReadSequence": 42,
    "readAt": "2026-10-26T12:01:00Z",
    "revision": 58
  }
}
```

Для `message.created`/`chat.updated` меняются `type` и `payload` на соответствующую полную модель. `eventId` — UUID события, при повторной доставке того же события не меняется. Это не cursor истории. Сообщения объединяются по `id`/`clientMessageId`, порядок — по sequence; снимки чата применяются по revision. Не обещаем exactly-once и не полагаемся на порядок прихода событий разных типов.

### Heartbeat, ошибки и токен

- Предложение: сервер отправляет стандартный WebSocket Ping каждые 25 секунд и ждёт Pong 10 секунд; затем закрывает не отвечающее соединение. Это control frames, не JSON-события. Конкретные интервалы подтвердить с учётом gateway.
- При истечении/отзыве access token соединение закрывается кодом `4001` (предлагаемый application code). Android обновляет токен обычным auth API и создаёт новое соединение. При ошибке авторизации handshake — HTTP `401`; при недостатке прав — `403`.
- После отключения сети Android повторяет соединение с увеличивающейся задержкой и jitter, не бесконечным немедленным циклом. Предложение — от 1 до 30 секунд.
- Нужны минимум два соединения одного аккаунта одновременно. Подтвердить лимит, предложение — 5; превышение при handshake — `429` с `Retry-After`, не тихое отключение другого устройства.
- Потеря доступа к чату немедленно прекращает его рассылку данному пользователю. Клиент при возвращении в foreground заново проверяет актуальное состояние через REST.

## 9. Восстановление пропущенных сообщений — CHAT-008

То же чтение истории, но в направлении вперёд:

`GET /api/chat/chats/{chatId}/messages?afterSequence=42&limit=50`

```json
{
  "items": [],
  "nextCursor": null
}
```

- `items` содержит полные Message с `sequence > afterSequence`, порядок `sequence ASC`. `afterSequence=0` — с начала истории.
- Если сообщений больше limit, `nextCursor` продолжает это направление; следующий запрос содержит только `cursor` и `limit`, не `afterSequence`. Cursor хранит направление и фиксированную верхнюю границу — lastSequence на момент первого запроса.
- `cursor` вместе с `afterSequence` в одном запросе — `400 INVALID_PAGINATION`. Отрицательное/нецелое afterSequence — `400`; значение больше текущего lastSequence — `400 INVALID_SYNC_POSITION`, клиент перепроверяет локальное состояние.
- `nextCursor: null` означает конец этого снимка, не отсутствие будущих событий. Новые сообщения после верхней границы поступают по WebSocket или в следующей синхронизации.
- Для обычного cursor запроса сервер продолжает направление, закодированное в cursor: назад из раздела 5 или вперёд из этого раздела. Нельзя перепутать порядок страниц.

Алгоритм Android: открыть WS → дождаться ready и буферизовать события → заново получить список/данные чатов → догрузить сообщения после последней **синхронизированной** позиции → объединить с событиями → продолжить реальное время. Новое WS-сообщение с большим sequence само по себе не продвигает подтверждённую позицию синхронизации: иначе можно пропустить более ранние сообщения. Перекрытие REST/WS допустимо, дубли убираются по id.

Для чатов, история которых ещё не загружена, достаточно последней страницы при открытии; всю историю всех чатов при каждом reconnect скачивать не нужно. Непрочитанные/прочтение восстанавливаются из свежего Chat, поэтому глобальный replay всех WS-событий не требуется. После foreground, reconnect и обнаруженного сбоя доставки выполняется REST-сверка; для открытого диалога нужна также периодическая сверка на случай незаметной потери события.

## 10. Единые ошибки

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Проверьте данные сообщения",
  "fieldErrors": { "text": "Сообщение не должно быть пустым" },
  "requestId": "request-correlation-id"
}
```

`code` и `message` обязательны; `fieldErrors` и `requestId` могут отсутствовать. Не отдавать stack trace, SQL или токены. Клиент принимает решение по code/HTTP-статусу, не тексту сообщения.

| HTTP | code / причина |
|---|---|
| 400 | `VALIDATION_ERROR`, `INVALID_PARTNER`, `INVALID_CURSOR`, `INVALID_READ_POSITION`, `INVALID_PAGINATION`, `INVALID_SYNC_POSITION` |
| 401 | `UNAUTHORIZED` — токен недействителен или истёк |
| 403 | `CHAT_NOT_ALLOWED` — запрещено создавать диалог |
| 404 | `CHAT_NOT_FOUND` для неизвестного **и чужого** чата; `USER_NOT_FOUND` для недоступного партнёра |
| 409 | `CLIENT_MESSAGE_ID_CONFLICT` |
| 410 | `CURSOR_EXPIRED` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 429 | `RATE_LIMITED`, заголовок `Retry-After` в секундах |
| 503 | `SERVICE_UNAVAILABLE` — временная недоступность |

Для существующего чужого чата и неизвестного chatId выбран одинаковый 404, чтобы не раскрывать существование диалогов. Это правило заменяет предварительное предложение 403 для чужого чата. Все операции с историей, отправкой и прочтением проверяют права одинаково.

## 11. Push — если сообщения должны приходить при закрытом приложении

WebSocket не заменяет push. Для уведомлений при выгруженном Android-приложении понадобится FCM и отдельный небольшой контракт:

- `PUT /api/user/devices/{installationId}` — JWT; JSON `{ "platform": "ANDROID", "pushProvider": "FCM", "pushToken": "..." }`, ответ `204`. Создать/обновить привязку текущей установки к аккаунту, повтор безопасен. installationId — UUID, созданный приложением. Новая авторизованная привязка той же установки заменяет прежнюю; права на другие установки по одному знанию их id не выдаются.
- `DELETE /api/user/devices/{installationId}` — JWT; ответ `204`, повтор безопасен. Удалить только привязку, принадлежащую текущему пользователю. При logout серверу желательно отзывать привязку этой установки вместе с сессией; одной локальной очистки токенов недостаточно для прекращения push.
- Payload уведомления: `type: "chat.message"`, `chatId`, `messageId` (строки). Текст сообщения не включать в push по умолчанию. При открытии Android читает сообщение через защищённое API.
- FCM token может меняться: PUT обновляет его. Невалидные токены удаляет сервер. Push может теряться/дублироваться, поэтому источником истины остаётся история сообщений.

Эти маршруты находятся в user-сервисе и нужны только вместе с фичей push. Сам текстовый чат и восстановление истории можно подключить без них; нельзя при этом обещать уведомления при закрытом приложении.

## 12. Что передать Android-разработчику для подключения

1. Подтверждённое правило создания диалога: пара или цель, условия допуска; реальные URL и согласованные схемы (OpenAPI для REST и описание WS-событий).
2. Доступное HTTPS/WSS окружение и два тестовых аккаунта; секреты передавать отдельно, не в Git.
3. Примеры успешных/ошибочных запросов в Postman/curl и последовательность открытия WS. Подтверждённые лимиты, TTL cursor, политика токенов и heartbeat.
4. Проверенные сценарии ниже — желательно автоматическими backend-тестами.

### Критерии готовности

- Создание диалога с обеих сторон одновременно даёт один chatId; посторонний не может читать, отправлять, отмечать прочтение или получать события.
- Сообщение после успешного POST есть в истории после рестарта сервиса; потерянный ответ и параллельный повтор с тем же clientMessageId дают одну запись.
- Пагинация истории и списка не пропускает элементы при новых сообщениях; одинаковые timestamps не нарушают порядок.
- Отключить получателя, отправить несколько сообщений, подключить снова: все сообщения восстанавливаются через REST, без дублей на пересечении с WS.
- Прочтение синхронизируется между устройствами, старый запрос его не откатывает, новое сообщение не обнуляется ошибочно.
- Истёкший JWT, неверный cursor, пустой/слишком длинный текст, rate limit и отсутствие доступа дают документированные ошибки.
- Рестарт между записью сообщения и публикацией не приводит к безвозвратной потере события; REST в любом случае возвращает сохранённое сообщение.

## Краткий список маршрутов

| Метод | Путь | Принимает | Возвращает |
|---|---|---|---|
| POST | `/api/chat/chats` | partnerId | 201/200 Chat |
| GET | `/api/chat/chats` | cursor?, limit? | 200 items: Chat[], nextCursor |
| GET | `/api/chat/chats/{chatId}` | chatId | 200 Chat |
| GET | `/api/chat/chats/{chatId}/messages` | cursor? или afterSequence?, limit? | 200 items: Message[], nextCursor |
| POST | `/api/chat/chats/{chatId}/messages` | clientMessageId, text | 201/200 Message |

| WS | `/api/chat/ws` | Bearer JWT в handshake | ready, message.created, chat.updated, chat.read |

Во всех строках, кроме публичного получения HTTPS avatarUrl, доступ осуществляется с JWT. Push-маршруты — отдельное расширение из раздела 11.
