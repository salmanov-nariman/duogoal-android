# Требования Android-клиента к backend HLT

Этот реестр — рабочий контракт между Android и backend-командой. Пункты со статусом «требуется» не считаются реализованными, пока backend-команда не подтвердила URL, схемы, коды ответов и окружение для проверки.

## Уже доступно

### AUTH-001 — регистрация и вход

**Статус:** доступно в исходном коде. 26 октября 2026 года `https://hlt.com/api/auth/validate` не ответил из среды разработки в течение 15 секунд; требуется проверить доступность ingress/staging окружения.

Используются:

- `POST /api/auth/register` — `{ username, email, password }` → `201 { username, email }`;
- `POST /api/auth/login` — `{ email, password }` → `200 { accessToken, refreshToken }`;
- `POST /api/auth/refresh` — `{ refreshToken }` → `200 { accessToken, refreshToken }`.

Желательно зафиксировать правила валидации `username` и `password`, а также полный формат всех 4xx/5xx-ошибок.

## Требуется для серверного завершения сессии

### AUTH-002 — отзыв refresh token при выходе

**Статус:** требуется. Текущий Android-клиент выполняет локальный выход без сети: удаляет токены и закрывает приватную навигацию.

`POST /api/auth/logout`

Запрос JSON: `{ "refreshToken": "..." }`. Успешный ответ `204 No Content`. Сервер отзывает переданный refresh token, чтобы его нельзя было использовать повторно. Операция должна быть идемпотентной: повторный logout для уже отозванного токена тоже завершается `204`. Для logout не должен требоваться действующий access token, который может уже истечь; аутентификационным секретом выступает сам refresh token. Backend-команда должна подтвердить контракт.

До появления endpoint клиент не обещает отзыв токенов на сервере или выход с других устройств. Ошибка сети при будущей попытке revoke не должна блокировать локальный выход.

### AUTH-003 — различимые причины отказа refresh

**Статус:** требуется уточнение контракта; клиент совместим с текущим `400` для невалидного refresh и `401`/`403` для отказа авторизации.

Для `POST /api/auth/refresh` желательно закрепить `401 { "code": "SESSION_EXPIRED", "message": "..." }` для истёкшего/отозванного refresh, а недоступность инфраструктуры возвращать как `503`. Это позволяет клиенту отличить обязательный повторный вход от временного сбоя. Отдельно согласовать поведение ротации при потере ответа: ограниченный период повторного использования прежнего refresh или идемпотентность запроса не должны приводить к потере сессии после временного обрыва сети.

## Требуется для основной идеи DuoGoal

### USER-001 — поиск партнёра

**Статус:** требуется.

`GET /api/user/search?q=<строка>&limit=20`

Ответ `200`: массив или страница пользователей с полями `id`, `username`, `displayName`, `avatarUrl` и кратким публичным описанием. Поиск не должен раскрывать email или другие приватные данные.

### GOAL-001 — жизненный цикл цели и приглашения

**Статус:** требуется согласование продуктовой схемы.

Для экранов создания цели, ожидания, приглашения и активной цели понадобятся операции: создать цель, пригласить партнёра, принять/отклонить/отменить приглашение, получить список собственных целей и получить цель по идентификатору. Перед проектированием endpoint'ов нужно согласовать модель цели: поля, типы статусов, сроки, отчёты и правила завершения.

## Общие требования к контрактам

- JSON в `camelCase`, UUID в строковом виде, даты — ISO 8601 UTC.
- Ошибки имеют стабильную машиночитаемую схему, например `{ "code": "...", "message": "..." }`.
- Пагинация — cursor-based; `limit` имеет максимальное значение, определённое backend.
- Для мобильного клиента доступно отдельное staging-окружение с HTTPS и тестовыми учётными данными.
