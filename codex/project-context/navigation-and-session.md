# Навигация и жизненный цикл сессии

Фича: `feature/app-navigation`, основана на `feature/duogoal-design-system`. HLT не изменяется.

## Навигация

- `ui/navigation/DuoNavigation.kt` содержит приватный `NavHost` на Navigation Compose 2.9.8 — совместимой с compileSdk 36.1 ветке библиотеки.
- Маршруты централизованы в `DuoDestination`. Реальные идентификаторы чатов/целей пока отсутствуют: контент этих экранов остаётся демонстрационным.
- `rememberNavController` сохраняет текущий экран и back stack при пересоздании Activity и восстановлении saved instance state.
- Переключение вкладок использует `saveState`, `restoreState`, `launchSingleTop`: сохраняются состояния разделов и не накапливаются одинаковые вкладки.
- Системная кнопка/жест «Назад» обслуживается Navigation Compose. Кнопки в шапках используют `popBackStack`.
- По завершении демонстрационного сценария «создать → выбрать напарника → отправить приглашение» экраны создания удаляются из стека. Возврат идёт к профилю.
- После принятия приглашения оно удаляется из стека и открывается активная цель.
- У входа нет общей истории с приватным `NavHost`. При регистрации «Назад» возвращает ко входу.

## Защита приватных экранов

`SessionGate` создаёт приватный `NavHost` только при `SessionState.SignedIn`. Во время восстановления, сетевой ошибки или выхода содержимое личных экранов не монтируется.

Back stack хранится в `SaveableStateHolder` под локальным ключом сессии `navigationKey`. Этот ключ сохраняется при refresh и меняется при новом входе. После выхода сохранённая навигация очищается; другой аккаунт начинает с ленты.

## Единый владелец сессии

`DuoGoalApplication` лениво создаёт один `AuthRepository` на процесс приложения и scope с `SupervisorJob`. Поворот не запускает повторный refresh и не уничтожает операцию локального выхода.

```text
DuoGoalApplication
└── AuthRepository: SessionState + операции входа/восстановления/выхода
    ├── HttpAuthApi: HTTP-запросы, без самостоятельного сохранения токенов
    └── EncryptedSessionStore: DataStore + Android Keystore

DuoGoalApp → SessionGate → AuthScreen или приватный DuoNavigation
               ↑
         StateFlow с учётом Lifecycle
```

## Состояния

| Состояние | Поведение |
|---|---|
| `Restoring` | Закрыть приватный UI, прочитать хранилище, выполнить refresh |
| `SignedOut` | Показать форму входа/регистрации |
| `SignedIn` | Открыть/восстановить приватную навигацию |
| `RestoreFailed` | Сохранить токены, предложить повторить попытку или выйти |
| `SigningOut` | Немедленно скрыть приватный UI, удалить токены на диске |
| `SignOutFailed` | Остаться вне приватного UI, предложить повторить очистку |

Недействительный refresh (нынешние HLT 400/401/403) удаляет локальную сессию. Сетевой сбой, 429, 5xx, некорректный ответ сервера и ошибка чтения диска не считаются подтверждением недействительности токена и не стирают его автоматически. Повреждённый шифротекст удаляется с предложением войти заново.

## Выход и конкурирующие запросы

- В профиле есть «Выйти из аккаунта» и диалог подтверждения.
- Выход работает без backend. Успех показывается после завершения транзакции очистки DataStore.
- Поколение операций и сериализация записи гарантируют: поздний login/refresh не сохраняет токены поверх завершённого выхода.
- `AuthViewModel` отменяет запрос и очищает поля при выходе/успешном входе. Отменённый запрос не может восстановить старый пароль в форме.
- Серверный revoke пока отсутствует. Выход очищает только это устройство; требование на `POST /api/auth/logout` записано в реестре backend.

## Данные и восстановление

- Access/refresh токены шифруются AES-GCM; пара ротируется одной транзакцией DataStore. Ключ находится в Android Keystore.
- Сохранённые сессии старой версии читаются; недостающий `navigationKey` создаётся и сохраняется после успешного refresh.
- Файл сессии исключён из cloud backup и переноса между устройствами: ключ Android Keystore не переносится вместе с ним.
- Форма хранит режим, email и имя в `SavedStateHandle`; пароль и loading туда не записываются. Поворот сохраняет введённый пароль в ViewModel, восстановление после смерти процесса требует ввода пароля заново.
- Строковые представления моделей с токенами/паролем скрывают их содержимое.

## Проверка без backend

Unit-тесты: восстановление/ротация, отказ сети и повтор, истечение токена, ошибки диска, повреждённое хранилище, logout, гонки поздних ответов, очистка формы и восстановление несекретных полей.

Instrumentation-тесты: реальный Navigation Compose, восстановление вложенного экрана, «Назад», изоляция разных сессий, блокировка приватных экранов; отдельно проверяются Android Keystore и DataStore на изолированных временных файлах.

```sh
./gradlew testDebugUnitTest connectedDebugAndroidTest assembleRelease lintDebug
```

Сквозной login/register/refresh с реальным HLT проверить после запуска backend. Новые защищённые API в будущих фичах должны интегрироваться с единым владельцем сессии; сам `NavHost` не выполняет HTTP-запросов.

Результат 26 октября 2026: 26 unit-тестов и 11 instrumentation-тестов на Medium Phone, Android 17, успешны; release-сборка успешна; Lint — 0 ошибок, 21 предупреждение. Проверен и визуально просмотрен холодный запуск обычной MainActivity. Связь с HLT не тестировалась: backend выключен по информации пользователя.
